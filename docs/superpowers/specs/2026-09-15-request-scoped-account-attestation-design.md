# 单次估时请求内复用账户检查

日期：2026-09-15。状态：用户已确认完整设计；实现、本地预检、全量回归及限定复审已通过；r9 合成对比在第二时点上下文证据失败后停止，原生验收未通过，尚未安装。

## 1. 目标及原目标关系

减少一次估时在上下文准备和模型提交之间重复进行完整账户检查的开销，不放弃每次模型调用的授权、账户归属、进程所有权和记账。

这是原生上下文继承计划的配套优化，不替代其有效上下文、三个配对检查点、准备时间至少降低 30%、首次有效 ETA 不退化及续估门槛。相同账户优化必须同时应用于原生和兼容持久会话路径，不能把公共优化算作原生继承独有收益。

## 2. 已确认的范围

- 仅在同一次 `prepareContext/prepareNativeContext → observe` 请求内，复用一次成功的账户检查；不同账户、对话、轮次、请求和进程之间不共享。
- 上限为原检查开始后 30,000 毫秒，且不得超过原账户证据有效期。命中、排队或后续验证均不续期。
- 无法证明可复用、发生变更或过期时，保留原完整检查。调用已进入不可逆边界时不隐式补跑模型。
- 每次 ETA 和压缩仍分别执行原授权、准入、账本及进程/终态记录；未知用量和历史失败记录不删除。
- 不读取主 Codex 凭据，不重新登录，不修改主账户、代理或主任务；不改变 API 路径。
- 不建立跨任务缓存、后台刷新服务或常驻全局账户会话，不改变原生分支清理时机，不合并、推送或安装未经验证的版本。

## 3. 现状证据

`observer-persistent-worker.ts` 的上下文准备与 `observe` 都调用 `ensure`，而 `ensure` 每次调用 `prepareSession`。`observer-identity-runtime.ts` 每次启动独立账户读取器；账户读取器通过两次账户读取、两次额度读取及前后路由检查确认一致性。普通无压缩 ETA 因此会进行两套检查、四次额度读取。

账户证据已有五分钟有效期上限，但这不是缓存。`desktop/observer-runtime.ts` 把结果转换为 invocation 与账户/路由/资产指纹时丢弃了时间字段。其 `metadataTail` 还串行化账户准备。直接删除第二次 `ensure` 会丢失现有身份变化检查，不能采用。

R8 首个检查点中，账户/进程阶段约占旧路径 9.03 秒、原生路径 9.48 秒；这些阶段还含进程与本地验证，不能声称所有时间都能省掉。该原生样本缺失早期标记，不能用作已通过的性能配对。

## 4. 选择

采用请求级一次性复用，而非跨任务账户缓存。跨任务复用可能节省更多准备成本，但需要新的共享失效、并行归属和生命周期机制，超出本轮范围。完全保留重复检查则不能直接减少已测到的公共成本，仍作为回退路径。

## 5. 凭证与数据流

### 5.1 身份层签发

一次正常完整检查结束后，身份层可同时签发内存中的不透明复用凭证。凭证不是用户授权，不是 API token，不可序列化、落盘、恢复或发送给模型；仅签发者能验证和消费。

凭证记录检查原始时间、单调时钟期限、原账户/路由/资产指纹、独立身份运行时实例与失效代次，并绑定被核实的独立认证文件与配置状态。所有状态仅存在于 HUD 进程内。检查前后状态不稳定时，不签发凭证，但不因此伪造一次检查失败或继续使用不稳定证据。

受保护目录及运行时验证继续沿用现有机制。只检查 HUD 独立认证目录内已知文件的元数据，不读取凭据内容、不解析 token。记录规范路径、文件身份、单链接/非重解析属性及大小、创建/修改/变更时间等可验证状态；缺失、读取失败、平台无法提供所需身份信息时，不允许复用。配置和发布资产保持原有精确校验，不用单独的文件时间戳替代既有哈希验证。

元数据比较不能防御同用户或管理员刻意伪造文件状态，也不能证明不可观察的远端状态永不变化；不作超出现有信任边界的承诺。普通账户切换、替换、写入、配置变化及已观察到的账户事件均使凭证失效；远端认证失败仍按真实失败处理，不自动在别的账户上重试。

### 5.2 请求和进程绑定

桌面运行时在原授权、精确 binding 和串行身份准备边界内传递凭证。worker 将其绑定到新准备出的输入对象、对话标识、轮次代次、source epoch/revision（如适用）、worker owner UUID 以及已启动进程的 PID/创建身份。

只有真实准备操作产生的输入对象可持有凭证；复制对象、重新反序列化、其他请求或外部传入相同标识均不能借用。身份凭证不能从 `prepareSession` 的裸返回值直接用于任意模型调用。

历史导入期间发生压缩时，丢弃请求的复用资格；该次后续 ETA 继续完整检查。压缩本身始终走完整准备和独立账本，不利用 ETA 的一次性凭证。这样不把中间模型操作或很长的上下文准备隐藏在一次复用里。

### 5.3 消费与失效

`observe` 只能原子认领一次对应凭证，先占用再进行异步验证；并发竞争者或再次调用必须失败或走正常检查，不能重复命中。取消或验证失败不返还凭证。

验证保留：当前用户授权、提供方失效代次、源请求/轮次、进程身份和健康状态、账户/路由/资产 binding、认证文件与配置前后状态、双时钟期限。时间回退、证据过期或失效状态读取不可靠时，不复用。

订阅设置变更、撤销、登出、身份运行时关闭、worker 重置/释放、原生分支替换及已观察到的 `account/updated` 事件必须使尚未使用的凭证失效。持久 RPC 增加有界的账户事件失效连接；它不能自己授予新授权或把账户标签当作身份。

## 6. 回退与不可逆边界

1. 在原账本准入之前，凭证不存在或验证未通过：仅执行一次既有完整 `prepareSession`，照常比较 binding；不能在失败账户与另一个账户间自动切换。
2. 完整检查导致进程/账户变化：沿用重置和 prepared-owner 失效规则；原生旧快照不能被悄悄提交到新进程。
3. 在真正发送前再次验证本次复用证明、期限、授权、进程及源代次。之前的异步排队、附件验证和账本写入不能使期限检查被绕过。
4. 若已准入但仍未发出时证明失效：按原机制收束未发出的准入并保留诊断，不运行模型，也不在同次操作中新增一次准入或自动补跑。后续请求由既有调度器决定。
5. 已发出后不再追溯撤销记账。真实失败、取消、退出不明和已知/未知用量沿用现有规则；任何迟到结果仍受源状态与新鲜度门槛限制。

最终文件核对与远端请求之间不是原子事务；不承诺消除现有检查到使用的全部竞态。事件失效、请求绑定、最终核对及原故障处理共同约束风险，不能以“最多 30 秒”代替这些措施。

## 7. 组件职责

- 新的身份层小模块负责一次性凭证、时间和代次生命周期；身份文件状态采集单独隔离，避免把账户读取器改成凭据读取器。
- `observer-identity-runtime.ts` 负责在完整检查前后采集状态，以及复用时保留本地 home/runtime/config 校验。
- `desktop/observer-runtime.ts` 扩展内部准备合同，保留精确身份 binding、授权与元数据队列，不把凭证暴露给 HTTP/MCP。
- `observer-persistent-worker.ts` 负责输入/源/进程绑定、一次消费、中间压缩作废与提交前检查；非持久和不支持该合同的测试/提供方使用原完整检查。
- 持久会话进程的账户事件仅传递失效信号；关闭时解绑，不能持有旧 worker 或给新账户自动授权。
- 诊断仅记录命中/未命中原因枚举、检查次数和阶段耗时；不记录身份文件元数据、指纹、路径、账户或凭据。

## 8. 验证与接受标准

先失败测试再实现，覆盖身份层、桌面合同和真实本地子进程 worker 边界。不得只测试 mock 回调次数而不验证实际派发和账本行为。

| 场景 | 必须证明的结果 |
| --- | --- |
| 同请求稳定状态，期限内 | 一次完整账户检查；第二处仅本地验证；恰好一次 ETA 派发和独立记账 |
| 30 秒边界、原证据提前过期、时钟回退 | 不复用；不得从消费时重新计时 |
| 复制输入、换对话/轮次、换 worker/进程、并发重复消费 | 不能共享凭证或造成重复派发 |
| 账户文件替换/写入/缺失、路由/资产变化、权限或身份检查失败 | 不复用；原失败和 binding 处理保持有效 |
| 账户事件、撤销、取消、关闭、原生重新准备 | 旧凭证不可恢复使用，无悬挂事件订阅 |
| 准备期间发生压缩 | 压缩独立完整检查与记账；后续 ETA 不复用旧凭证 |
| 准入后、派发前故意延迟至过期 | 零模型派发，账本无未处理遗留，无隐藏重试 |
| 已派发后失败、已知/未知用量、退出不明 | 保留现有终态、用量和清理语义 |

先在不运行模型的同请求调用链上测完整检查次数、本地复核及总准备耗时，再进行有界合成验证。用户已授权必要模型调用，不再为每次调用重复询问，但仍保留独立审计、失败后诊断和用量记录，不盲目重试。

全量串行回归、类型检查和构建在实现里程碑运行。新的账户一致性边界需要一次针对性安全/认证/账本复审，采用 `gpt-5.6-sol / medium`；这是本次新增边界的必要审查，不重跑旧架构的整套重复审阅。实现或定向测试使用 `gpt-5.6-luna / high`（跨模块）或 `medium`（聚焦测试），至多一次修复复审。

复用成功且安全门槛通过，仍不等于原生路线可上线；原生上下文可靠性和公平配对性能门槛独立保留。不通过则保留原完整检查，不能用局部准备减少冒充总目标完成。
